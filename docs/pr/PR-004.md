# PR-004: Tilstandslaget — PostgreSQL for M-2 og frekvensteller + attestasjonssignatur

**Draft: Claude.ai · Branch: `pr-004-tilstandslag-adr001` · Svar på ADR-001s fire bindende krav.**

Draftet er utviklet mot **faktisk main** (a6097f3, syntet med raw.githubusercontent) og **kjørt mot ekte PostgreSQL 16** lokalt: 74 tester grønne totalt (62 fra main + 12 nye), inkludert kappløpstest med 20 samtidige tilkoblinger.

## ADR-001-krav → implementasjon → bevis

| Krav | Implementasjon | Bevis |
|---|---|---|
| 1. Atomisk reservasjon i databasen | `PgTellerLager.reserver`: én transaksjon med `pg_advisory_xact_lock` på nøkkelen + betinget `INSERT … WHERE (count) < maks RETURNING`. Streng bool-kontrakt fra `TellerLager` overholdt. Låsen er xact-variant — slippes automatisk ved commit/rollback/krasj | `test_atomisk_reservasjon_under_ekte_kappløp`: 20 tråder, egne tilkoblinger, maks=3 → nøyaktig 3 True, 17 False |
| 2. Logg + reservasjon i samme transaksjon | `sikker_beslutning_pg`: reservasjon og loggpost committes i SAMME transaksjon. Kappløpstaper får `brudd_utfall`-riktig beslutning logget og null reservasjon. Filvariantens kjente skjevhet («reservert men ikke logget») kan ikke oppstå | `test_reservasjon_og_logg_i_samme_transaksjon` |
| 3. Kryptografisk attestasjonsverifikasjon | Ny modul `attestering.py`: HMAC-SHA256 over kanonisk innhold, nøkkelregister per verifikator med rotasjonsstøtte, konstant-tids sammenligning, fail-closed. Porten ligger i `sikker_beslutning_pg` (nettverksinngangen) — motoren er urørt. Nøkler fra env/0600-fil, aldri repo; åpne filrettigheter er feil, ikke advarsel | `test_manipulert_innhold_avvises`, `test_signaturport_stopper_usignert_hendelse`, `test_nokkelfil_med_apne_rettigheter_avvises` m.fl. |
| 4. Tenant-isolasjon fra første migrasjon | `001_init.sql`: `tenant` i indeks på begge tabeller; alle teller-spørringer filtrerer på tenant (del av nøkkelen) | Skjemaet + kappløpstesten (nøkkel inkluderer tenant) |

**I tillegg, utover kravene:** append-only for revisjonsloggen er nå håndhevet AV DATABASEN — triggere avviser UPDATE/DELETE/TRUNCATE uansett hvem som spør (`test_revisjonslogg_er_append_only_i_databasen`). Og DB utilgjengelig → STOPP, aldri «fortsett uten logg» (`test_db_nede_gir_stopp_aldri_sideeffekt`).

Ingen endringer i `engine.py`/`audit.py` — signaturporten ligger i inngangen, ikke i motoren. Filvarianten `sikker_beslutning` beholdes, men skal per ADR-001 merkes `KUN UTVIKLING` (én docstring-linje — overlates til Claude Code som eier filen etter P1-rundene).

## Bindende for PR-005 (API)

- API-et MÅ kalle `sikker_beslutning_pg` med `nokler=last_nokler()` på ALLE nettverksforespørsler. `nokler=None` er kun lovlig i lokal utvikling og `run_synthetic`.
- Verifikator-modulene (M-14, M-42, …) utsteder attestasjoner via `attestering.signer` med egen nøkkel fra registeret.

## CI og staging

- CI: `pip install`-linjen trenger `psycopg[binary]`. DB-testene hopper i CI (ingen DSN) og kjører på staging — alternativt kan CI få en PostgreSQL-service-container senere.
- Staging: kjør `deploy/staging/oppsett-postgresql.sh` som root (idempotent: installerer PostgreSQL, oppretter roller/databaser, genererer 0600-miljøfil med DSN + attestasjonsnøkler, kjører migrasjonen), deretter `set -a; . /etc/disponit/staging.env; set +a && python3 -m pytest platform/core/tests -q` → 74 forventet. Dette er m01s første reelle staging-port.

## Kjente avgrensninger (deklarert)

- Advisory-lås serialiserer per nøkkel — riktig og raskt nok nå; ved svært hete nøkler kan PR-006+ vurdere bøttetabell med `UPDATE … WHERE antall < maks`.
- Nøkkelrotasjon er manuell (legg til k2, bytt, fjern k1) — automatisering hører til M-29.
- `run_synthetic.py` kjører fortsatt filvarianten; PG-variant av synthetic kan legges til når staging kjører.
